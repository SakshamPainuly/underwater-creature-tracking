6. PERFORMANCE METRICS: WHICH ONES, AND WHY
--------------------------------------------------------------------------------

  Metric        What it means for lobster detection
  ------------  ----------------------------------------------------------------
  IoU           Overlap between a predicted box and the labelled box
                (0 = none, 1 = identical).
  Precision P   Of the boxes the model draws, the share that are real lobsters.
                Low P = false alarms.
  Recall R      Of the labelled lobsters, the share the model finds.
                Low R = missed lobsters.
  F1            Balance of P and R (harmonic mean). Used to pick the operating
                confidence on val.
  mAP50         Average precision over all confidence levels, a detection counts
                when IoU >= 0.50. Answers "was the lobster found?".
  mAP50-95      The same averaged over IoU 0.50, 0.55, ..., 0.95. Also rewards
                tight, well-placed boxes.
  TP / FP / FN  Found lobsters / false boxes / missed lobsters (confusion matrix).
  False detections on empty images: how often the model "sees" a lobster in a
                frame that has none.

Why we report several: one number hides trade-offs. E004 had better precision
but missed more lobsters; only P, R, mAP and the confusion counts together show
that. Per-session and red-light results show where the model is weak.

Not used: tracking metrics (IDF1, HOTA, MOTA). There are no ground-truth track
IDs and the frames are 10-30 s apart, so tracking cannot be scored. No physical
units (cm): there is no camera calibration, so everything is in pixels.

7. THE SELECTION METRIC USED TO DECLARE THE BEST MODEL, AND THE RULES
--------------------------------------------------------------------------------

Selection metric: VALIDATION mAP50-95 (class lobster), declared on 2026-11-11
before any tuning run (D-038). Before that, the project's selection metric was
val mAP50; it was switched for Model A runs from E011 on.

Why mAP50-95:
  1. Trajectories are built from box positions in pixels, so we need the
     lobster to be FOUND and the box to be PLACED WELL. mAP50 only checks the
     first; mAP50-95 checks both.
  2. Ultralytics already uses mAP50-95 to pick the best epoch (fitness), so one
     criterion runs from "best epoch" to "best run" to "final model".
  3. It is stricter, so small gains in box quality are not hidden.
  mAP50, P, R and confusion counts are always reported next to it.

Rules, fixed before the runs they govern:
  - Seeds measure noise: round 1 ran each size with 3 seeds; the spread (range)
    of the seeds is the noise level.
  - The smaller model wins a tie: a bigger model is chosen only if its gain is
    larger than the seed noise.
  - Round 2 bar: a run replaces the round-1 choice only if its val mAP50-95 is
    above 0.62542 = yolo26m seed mean 0.61127 + its seed range 0.01415.
  - Test data never chooses anything; only the declared run is tested, once.
  - Time-boxed queue: a run starts only if its worst case ends before the
    Kaggle deadline, so no run is cut off; skipped runs are "not run (time)".
  - Ultralytics model.tune() (genetic search) was not used: it needs dozens to
    hundreds of runs, far beyond the Kaggle quota.

10. TUNING ROUND 2: WHICH TRAINING SETTINGS? (E020-E029, D-040 / D-043)
--------------------------------------------------------------------------------

Design: every run uses a 30-epoch schedule with patience 30, so it always
completes: the learning rate decays fully and the last 10 epochs run without
mosaic. 30 epochs because round-1 best epochs were 16-31 and ten runs had to fit
two T4s within 9.5 h. Five combinations on yolo26m (parent E012) and yolo26l
(parent E013), seed 0. Kaggle 2 x T4, commit 97810a5, session 9.05 h.

  C1  schedule only (the control)
  C2  + AdamW, lr0 0.001, momentum 0.9 (half of auto's 0.002)
  C3  + mixup 0.1 (blends two training images: a regulariser against overfitting)
  C4  + AdamW lr0 0.001, momentum 0.9, weight decay 0.001, mixup 0.1
  C5  + freeze 10 (backbone frozen: only neck and head train)

18. WHY WE DID WHAT WE DID (REASONS FOR EACH STEP)
--------------------------------------------------------------------------------

  Step                         Reason
  ---------------------------  ---------------------------------------------------
  Rebuild Harsh's data on our  His split had 5 of our 6 test sessions in train/val.
  own split + leakage check    Training on images made from test frames would make
                               the test score meaningless.
  Keep val/test unmodified     So every model (E001 ... E027) is scored on exactly
                               the same real frames: a fair comparison.
  Hold out Zenodo sk           Our test shares sites with train; sk is the only
                               check on a truly new location.
  E007: all data at once       Short deadline; the user chose one run over a data
                               ladder (adding sources one at a time).
  Change the schedule          E007 and round 1 peaked early with the learning rate
                               still high and never reached the low-LR / no-mosaic
                               phase; a complete 30-epoch schedule fixes that.
  Try bigger models            YOLO26s may be too small for 4,111 varied images;
                               round 1 tested s, m and l.
  3 seeds per size             To know how much scores change by chance alone, so
                               a "gain" smaller than that is not called a gain.
  AdamW with lower lr0         Auto picked AdamW lr 0.002; half of it tests
                               whether a gentler update fine-tunes better.
  Mixup and weight decay       E007 overfit after epoch 28 (val loss rose);
                               both are regularisers against overfitting.
  Freeze backbone (C5)         Tests whether keeping COCO features fixed reduces
                               overfitting; it did not (worse).
  One metric (mAP50-95)        Avoids picking whichever metric looks best after the
                               fact; it measures both finding and box placement.
  Bar = mean + range           A single new run must beat the round-1 choice by more
                               than seed noise to replace it.
  Test once, declared first    Any test result that influences a choice is no longer
                               an unbiased estimate.
  Val-only evaluation          The final-test records keep no per-image results; val
                               per-image results show false alarms on empty frames
                               and weak sessions without touching the test set.

  - Image enhancement (E004, before Week 2): fewer lobsters found.

  - Freezing the backbone (E028, E029): the worst runs of round 2.

21. LIMITATIONS AND OPEN QUESTIONS
--------------------------------------------------------------------------------

  - v1 test sessions share sites (mostly also dates) with training sessions:
    the v1 test measures NEW SESSIONS at known sites, not new sites. Zenodo sk
    is the only new-site test, and there the model is weak.
  - 19 configurations were compared on the same 324 val images, so E027's val
    score is optimistic. Its margin over the bar (0.0025) is smaller than seed
    noise (0.014): another seed of the same settings could fall below it.
    Only the test results are unbiased.
  - One seed of the final configuration; leave-site-out cross-validation was
    planned but deferred.
  - Round-2 runs are single-seed, so the "patterns" in section 10 are not proven.
  - Training labels partly rest on an AI label review that no person checked;
    up to 29 train frames have a lobster without a box.
  - Substrate and visibility metadata are mostly missing; zExtra (436 frames)
    has no labels and is only shown in the GUI.
  - UNKNOWN: false detections on the 27 empty v1 test images and 285 empty sk
    images, and per-session test results (the test records keep no per-image
    predictions; measuring them would need a new decision).
  - Kaggle quota: very little was left after all runs (user-reported).
    INFERRED: that is why a second seed and cross-validation were not run.
  - No tracking metrics, no physical units (see section 6).
